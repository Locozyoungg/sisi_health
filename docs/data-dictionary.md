# Data Dictionary

Every table and column in the SISI Health PostgreSQL 16 database, read from
`backend/app/models/*.py` and the Alembic migrations
(`backend/migrations/versions/0001`–`0010`). 54 application tables across 8
schemas, plus Alembic's own `alembic_version`.

**Reading the encryption marks:**

| Mark | Meaning |
|---|---|
| **[sealed]** | `BYTEA` ciphertext: AES-256-GCM (12-byte random nonce ‖ ciphertext). See the accuracy note at the end — payloads are currently sealed **under the master key**; the `*_key_id` column records the owner's row in `core.data_keys` |
| **[key]** | `core.data_keys.wrapped_key`: 32 random bytes wrapped by the master key (the per-owner key record; deletable on erasure) |
| **[hmac]** | keyed hash with the `SISI_PHONE_PEPPER` (`HMAC-SHA256`) — non-reversible lookup value |
| **[sha256]** | unkeyed SHA-256 hex digest |
| **[pseudonym]** | random UUIDv7, unlinkable to identity; set to NULL on erasure |
| plain | stored in clear |

Conventions: all timestamps `TIMESTAMPTZ`, stored **UTC** (display is
Africa/Nairobi); all primary keys UUIDv7 generated by the application
(`core.ids.uuid7`) — no auto-increment id is exposed except
`audit.audit_events.seq`, which is the chain position only.

| audit_events | resource_id | UUID | yes | |
| audit_events | payload | JSON | no, `{}` | sanitised in the service layer: **never names, phone numbers, or symptom content** |
| audit_events | prev_hash | BYTEA | no | previous row's `row_hash`; the first row chains from `\x00` |
| audit_events | row_hash | BYTEA | no | SHA-256 chain hash **computed by a DB trigger** |
| audit_events | created_at | TIMESTAMPTZ | no | |

DB objects (migration 0001): extension `pgcrypto`; function
`audit.chain_insert()` (takes `pg_advisory_xact_lock(424242)`, reads the last
`row_hash` by `seq`, sets `prev_hash`/`row_hash`); function
`audit.block_mutation()` (raises `audit.audit_events is append-only`);
triggers `audit_chain` (BEFORE INSERT), `audit_no_update`, `audit_no_delete`.
Hashing in the DB means the writer and the Python verifier can never drift
(assumption A13).

## Accuracy notes (verified against source, not smoothed over)

1. **Envelope sealing is one layer short of the design.** `DatabaseKeyProvider.wrap()`
   encrypts with the **master key** (`AESGCM(self._master)`), and `seal_json()`
   calls `provider.wrap(...)` while storing the *data-key row's id* in `key_id`.
   So today's payload ciphertext is sealed under the master key; the per-owner
   `core.data_keys` row exists (and is deleted on erasure, and is what
   `key_id` points at) but its `wrapped_key` material is not what protects the
   payload. Consequences: compromising the master key alone decrypts all
   payloads (the per-record key adds no second layer), and per-record key
   rotation does not currently re-key anything. `open_json()` only checks that
   the `DataKey` row exists. **This is a genuine hardening item, not a
   documentation artifact** — see `/docs/hazard-log.md` review and Phase 9.
   Docs elsewhere describing "per-record data keys wrapped by the master key"
   should be read with this note.
2. **Owner types in use**: `user`, `staff`, `corridor`, `assessment` (school
   assessments) — `owner_type` is free text with no constraint or enum.
3. `core.users.phone_encrypted`, `core.users.birth_date_encrypted`, and
   `core.staff_users.totp_secret_encrypted` have **no `key_id` column**; their
   key row is resolved by `(owner_type, owner_id)`.
4. Columns typed UUID with **no FK** (polymorphic or unenforced):
   `data_keys.owner_id`, `config_values.updated_by`,
   `consent_events.recorded_by`, `dsr_requests.handler_id`,
   `rule_versions.created_by`, `rule_activations.author_id`/`approver_id`,
   `audit_events.actor_id`/`resource_id`, `wallets.owner_id`,
   `wallet_ledger.ref_id`, `consult_events.actor_id`,
   `sharing_approvals.resource_id`, `surgery_events.actor_id`,
   `tracker_events.actor_id`. No DB-level referential integrity there.
5. `school.voucher_redemptions.pharmacy_id` is `NOT NULL` **and**
   `ON DELETE SET NULL` — contradictory: deleting a pharmacy row would fail
   the constraint. Flagged for a fix; it does not affect redemption paths today.
6. Status/enum columns with **no documented allowed values** (the doc must not
   invent them): `core.schools.status`, `core.staff_users.role`,
   `corridor.consult_events.event_type`, `corridor.surgery_events.event_type`,
   `ai.content_chunks.audience`, `diary.processing_flags.flag`,
   `corridor.pricing_stubs.currency`. The `corridor` tables whose statuses
   *are* pinned have migration comments, listed above.
7. `core.student_contact_map` and `core.guardians` have **no production write
   path** yet — they are written by `backend/scripts/seed_school_demo.py` and
   read by the nurse re-identification path. The enrolment flow that populates
   them for a real school is an ops task.
8. `ai.chunk_embeddings.embedding`'s SQLAlchemy-mapped type (`JSON`) does not
   match the pgvector branch's DB type (`vector(768)`); the model is
   metadata-only and all writes go through raw SQL casts (by design, CC-4).
